# Architecture

How the pieces fit together, and which milestone builds each. The reasoning
behind the choices is in the [ADRs](adr/README.md); this document is the map.

## Shape

```
                        browser
                           │
            ┌──────────────┴───────────────┐
            │                              │
     tiles (Caddy :8081)            web (Caddy :8000)
     PMTiles · glyphs · sprites      SPA  +  /api/* ──► gateway (:8080)
            │                                                │
            │                              ┌─────────────────┼─────────────────┐
            │                              │                 │                 │
     ┌──────┴──────┐                 routing (:8002)   geocoding (:2322)   data/
     │  data/      │                  Valhalla            Photon          coverage
     │ *.pmtiles   │                                                      manifest
     └─────────────┘
```

Two rules hold the shape together:

1. **The browser talks to exactly two origins**: the tile host and the gateway
   (SPEC §2.2). It never sees Valhalla or Photon.
2. **Nothing reaches a third party at runtime** (SPEC §0.1). Every tile, glyph,
   sprite, search result, route and elevation value comes from a service in
   `infra/docker-compose.yml`.

## Workspaces

| Path              | What it is                                | Build output      |
| ----------------- | ----------------------------------------- | ----------------- |
| `apps/web`        | Vite + React + TypeScript frontend        | static bundle     |
| `apps/gateway`    | Fastify service owning `/api/*`           | single ESM bundle |
| `packages/shared` | DTOs, geo primitives, coverage constants  | — (source)        |
| `packages/style`  | MapLibre styles generated from TypeScript | `dist/*.json`     |
| `packages/icons`  | Original SVG POI set                      | sprite sheets     |
| `pipeline/`       | Dockerised data build                     | `data/`           |
| `infra/`          | compose, Caddy, env examples              | —                 |

Internal packages export TypeScript source rather than compiled output
([ADR-0002](adr/0002-pnpm-monorepo.md)), so `pnpm typecheck` works on a clean
checkout without a prior build.

`packages/shared` is the contract. `Place`, `Route`, `Waypoint` and every API
DTO are defined once and imported by both sides, so the frontend and the
gateway cannot drift.

## The gateway

The single public API ([ADR-0008](adr/0008-fastify-gateway.md)). Four jobs:
coverage enforcement, upstream normalisation, caching and rate limiting, and
localised errors.

| Endpoint                         | Milestone | State after M0                                          |
| -------------------------------- | --------- | ------------------------------------------------------- |
| `GET /api/health`                | M0        | live — per-upstream rollup                              |
| `GET /api/coverage`              | M0        | live — polygon, or bbox fallback flagged `exact: false` |
| `GET /api/search`                | M4        | validates, then `501`                                   |
| `GET /api/reverse`               | M4        | validates + coverage-checks, then `501`                 |
| `GET /api/place/:osmType/:osmId` | M4        | validates, then `501`                                   |
| `POST /api/route`                | M5        | validates + coverage-checks, then `501`                 |
| `POST /api/elevation`            | M5        | validates, then `501`                                   |

The endpoints that land later are wired now with their real validation and
coverage checks. A malformed request gets `400` and an out-of-coverage one gets
`422` today; only the upstream call is missing. That makes the SPEC §2.2
contract testable from M0 rather than from M4.

Every non-2xx response has the same shape:

```json
{ "error": { "code": "OUT_OF_COVERAGE", "message": "Fuori dall'area coperta dalla mappa" } }
```

## Coverage

Coverage is defined twice, deliberately
([ADR-0011](adr/0011-coverage-enforcement.md)):

- `ITALY_BBOX` in `packages/shared` — a cheap pre-filter and the source of the
  camera's `maxBounds`. Never authoritative: a box containing both Lampedusa
  and Vetta d'Italia also contains Corsica and half of Slovenia.
- `data/coverage.geojson` — generated by pipeline step 2 from OSM
  `admin_level=2` boundaries. Authoritative, evaluated by point-in-polygon in
  the gateway.

The same polygon is served to the client for the render mask, so enforcement
and rendering can never disagree.

Before the pipeline has run the gateway degrades to the bbox and says so
(`exact: false`), which is why an M0 stack runs end to end without pretending
its coverage is correct.

## Client state

Three tiers ([ADR-0013](adr/0013-client-state.md)):

- **URL** — camera, base layer, waypoints, routing mode, selected place. The
  source of truth, not a mirror, which is what makes back/forward correct for
  free. Codec and tests: `apps/web/src/lib/url-state.ts`.
- **Zustand** — ephemeral UI: panel state, sheet snap point, overlay toggles.
- **TanStack Query** — server data, with caching and cancellation (from M4).

## Styles

Generated from TypeScript against shared tokens and validated with the official
MapLibre validator in CI ([ADR-0009](adr/0009-styles-from-typescript.md)).
`packages/style/src/tokens.ts` is the single source for both the cartographic
palette and the UI design tokens.

M0 ships `base` only — land background plus coverage mask — to prove the
generate-and-validate loop. The four full styles are M2, M3 and M6.
